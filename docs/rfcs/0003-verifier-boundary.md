# RFC 0003：可替换验证器与执行回执边界

日期：2026-09-20。状态：设计草案，尚未实现执行器。

## 下一步要完成什么

v0.3 已能登记“请检查这个版本的这一部分”。下一步是让独立服务接收经授权的任务并返回可检查的运行记录，而不是让用户手工选择 Lean 或 AI 标签就获得系统认证。

## 分开两类记录

**参与者报告**继续开放提交，可以是支持、质疑、解释、推测或转述。它不会自动变成经过运行的证据。

**执行回执**应记录绑定版本、请求标识、执行器标识、工具和依赖版本、被检查命题、输入与输出摘要、日志、资源限制、执行结果和失败原因。回执说明实际运行了什么，不宣称整个研究框架或现实解释已经正确。

状态至少区分成功完成检查、检查未通过、证明不完整、发现具体反例、工具不支持、资源耗尽、运行错误与无法判定。具体类型随执行器确定；普通编译成功不能直接作为完整证明状态。

## 权限与同意

执行器只能读取所授权的输入并产生运行回执；没有编辑原文、删除评论、决定全站排序或操作资金的能力。请求记录中的 local_record_only 不可由后台偷偷提升为外部执行同意。

外部模型需要按目标服务说明数据范围与成本。取消待执行任务后不可继续开始外发；已发出请求的取消无法保证远端撤回，必须说明实际发生的行为。用户稿件和评论中的指令始终当作数据，不改变工具权限。

## 实现顺序

先建立回执契约与无外部副作用的固定测试夹具，检查请求与结果绑定、取消、重试、重复回执、失败状态和权限越界。夹具输出明确标为测试，不伪装成 AI 或 Lean 结果。

随后接入一个固定环境中的可信示例，再审查运行不受信任 Lean 工程或程序所需的隔离、资源、网络与秘密管理。仅超时不是沙箱；仅容器化也不能不经审查就宣称安全。

最后设计多个验证器并存、读者选择与可复核回执。不同验证器意见不一致时保留差异，不由一个中心删除不受欢迎的结果。

## 完成条件

针对同一版本的两种服务可以给出不同结果；普通参与者不能伪造运行回执；执行失败不影响发表；取消与重试不会误外发；任何服务退出后作品仍可阅读并导出。未满足这些条件前，平台不得显示自动核验已上线。
