# RFC 0032：论文字节的时间覆盖与多副本保存

状态：实施中。日期：2026-11-06。作者：维护者 AI。用户要求落实审阅意见；本地进度与未完成项见 PROJECT_STATE，尚未完成线上部署或第三方归档。

来源：用户问“用分布式数据链保存每个人的文章，可行吗？”，并要求写成方案。关联 [RFC 0029](0029-record-chain-and-anchoring.md)、[RFC 0030](0030-public-mirror.md)、ADR 0003 的 O1、O4、O5。

## 结论

1. 比特币继续只存证明，不存全文。
2. 先补一个已有缺口：现在的时间戳没有覆盖 PDF、TeX 这些论文文件。
3. 全文靠多份独立副本保存，副本的范围由作者的许可决定。
4. Arweave 这类不可删除的永久存储，不作为默认存储；以后最多是作者主动选择的附加项。

## 要解决的问题

### 已核对的现状（2026-11-06，线上 `eksmu.com`，只读）

用 `tools/eksmu_verify.py pull` 拉取线上镜像：校验通过，共 7 个文件、108 KB。

| 项目 | 实际情况 |
|---|---|
| 公开记录 | 6 条：2 个账户、2 篇作品、2 个版本；两篇作品都属于站长账户 |
| 记录链 | 长度 6，最后链头 `6ba65dac…`；3 个锚点均已确认（区块 #973733、#973939、#974090） |
| 版本记录的正文 | 分别约 1.8 千字和 600 字，是收录说明；另有摘要、作者、许可和参考文献 |
| 论文文件 | K4 PDF（6.5 MiB）、arXiv 源码包和编译产物都是附件 |
| 发表快照 | 0 个，所以镜像里没有任何附件字节 |
| 附件摘要 | 不在任何上链记录中。`8fe99f0c…` 只出现在 AI 分析元数据里，`727d7c1f…` 不在镜像中 |

### 由此得出的三个缺口

**缺口 1：时间戳没有覆盖论文全文。** 比特币锚定的是版本记录。对这两篇论文，它能证明标题、摘要和收录说明的时间，不能证明 PDF 或 TeX 的时间。站内作品页写的是“本版正文”，这在字面上成立，但读者很容易理解成整篇论文。

这两篇论文另有 Zenodo 或 arXiv 的外部日期，所以受影响较小。如果作者只在本站上传 PDF，它就没有外部时间证据。

**缺口 2：对外说明超出了实际能力。**

- [`/openness.html`](../../eksmu/static/openness.html) 第 34 行称“用镜像在本地完整重建与继续运行”，第 44 行称镜像“含所有作品、附件”，第 57 行称可用于“异地重建”。线上镜像实际不含附件字节。
- `eksmu-protocol` 的 README 称工具复制 “entire public record”，也有同样的问题。
- 2026-11-04 录制的视频素材 `clip6-openness-chain-*` 拍到了这一页。

**缺口 3：全文实际上只有一份在线副本。** 附件字节只在单个在线对象存储桶里（软删除保留 30 天）。GCS 模式下，每日备份只记录并核对附件摘要，不复制字节。整个系统在同一家云上。第二节点（O5）还没有运营者。本 RFC 没有查到有外部人员在定期保存镜像。

### 为什么冗余重要

时间戳只证明哈希。没有原始字节，证明就无法使用。所以覆盖（缺口 1）和保存（缺口 3）是同一个问题的两半。

## 方案

### 分层

| 层 | 内容 | 能否删除 | 默认 |
|---|---|---|---|
| 时间层 | 比特币与 OpenTimestamps，只含链头摘要 | 不能 | 已开启 |
| 承诺层 | 记录链，覆盖版本记录和附件摘要 | 内容可删，摘要保留 | 本 RFC 扩展 |
| 证明副本 | 链条目、锚点和 `.ots`，不含正文 | 摘要可被猜测或关联，外部副本不保证删除 | 建议开启 |
| 内容副本 | 记录和附件字节，受许可限制 | 受控副本可按已验证声明移除，外部副本不保证 | 作者同意后开启 |
| 永久存档 | Arweave 等 | 实际上不能 | 不开启，见“暂缓” |

### 阶段 P0：先改对外说明

不等工程完成，先把 `/openness.html`、作品页和 `eksmu-protocol` README 改成实际情况：

- 时间证据覆盖版本记录，附件目前不在覆盖范围内。
- 镜像包含公开记录和发表快照；未固定进快照的附件不包含在内。
- 视频素材 `clip6` 在成片前重录。

这一步可逆，也不涉及数据变更。

### 阶段 P1：附件进入记录链

候选记录类型 `material` 不包含文件名等不必要的公开元数据。附件元数据、对象存储与主记录链不共享事务：先保存并校验附件，在主记录库的事务中追加承诺与链条目，通过稳定附件 ID 实现可重试的对账；必须设计并验收自动对账、故障告警和逐附件状态后才能用于生产。裸文件摘要仍可能被用于猜测验证，发布前须评估隐私风险。

本地 `material_chain.reconcile` 仅用于合成数据实验，逐条校验字节并幂等补链，全部标记为补链；没有自动上传对账或逐附件状态，也没有完成公开协议工具的兼容升级，**不得用于生产数据**。仅有该原型不意味着附件已获得时间证据。

不把摘要写进 `revision`：附件可以在版本发表之后追加，而版本摘要已经固定。

- 现有附件以 `backfilled` 补链。时间证据只能从补链后的下一次锚定开始，不能回溯，页面要如实写明。
- 作品页按文件显示时间证据：哪个文件、摘要、被哪个区块覆盖、是否为补链。
- 编译产物标记为 `derived`，并指向源码包。
- 工具 `eksmu_verify.py` 的 `RECORD_TYPES` 和 `store.validate` 都是封闭集合，旧核验工具遇到新类型会失败。因此要同时升级到 `eksmu.public-mirror.v2`，更新 SPEC，并让新工具继续能读 v1。

发表快照（RFC 0015）继续保留，作为作者主动固定的完整材料包。作者声明进链仍按 RFC 0030 的后续计划，不在本 RFC 内。

### 阶段 P2：删除内容，但不改写链

过去的做法都是改写记录链：

- 2026-10-31 删除广告作品时，一个已确认的锚点（#973863）也被移除，旧镜像会看到链被截短。
- 同日删除账户、清除公开显示名中的站长邮箱时，是重算未锚定部分的链头。

这些操作在当时规模下可控，但以后不能这样做。新规则：

```text
redactions[] = { seq, record_id, record_sha256, reason_code, decided_at, notice_id }
```

- 链条目和摘要保留，记录内容和附件字节移除。
- 核验工具可用条目里的 `record_sha256` 继续折叠链头，报告“某条内容据声明已移除”；链摘要一致不能冒充内容完整、引用有效、理由正当或声明真实。
- 已确认的锚点不再删除。
- 适用范围：隐私泄露、侵权、违法内容和其他 CHARTER 规定的情形。理由要公开，但不复述敏感内容。
- 校验结果不能证明被移除的内容是什么，也不能证明移除是否正当；这条要写进工具输出。

**实施契约（尚未接入线上）：**

1. 核验输出至少分别报告链折叠、原文完整性、后续作者／作品／版本引用、删除声明认证、外部时间证明和与独立保存的链头比较。作者或版本缺失时，其依赖关系标为不可核验；不默认为通过，也不让无法核验的引用成为任意内容有效的证据。格式错误、未声明的缺失、摘要或已知链头不匹配必须失败。
2. 声明要绑定精确链序号、记录 ID 和摘要，规定版本、签署人及密钥轮换、追加与撤销规则；同步端必须验证可信签名及来自独立持久检查点的连续性后才可考虑删除。无认证或检查点回滚时停止自动删除并告警。即便签名有效，也只能说明授权方签发了声明，不证明移除理由正当。签名密钥、轮换与复核机制尚须单独设计实现；本 RFC 不授权目前依据未签名清单自动删除。
3. 删除处理逐项登记源附件、正文、发表快照、预览、派生物、缓存、索引和受控备份；按对象依赖与共享引用处理，避免误删其他作者仍在使用的同字节对象。备份恢复在重新对外提供前必须应用可信删除记录，并验证恢复后内容；如暂时无法清除离线备份，记录保管、到期及隔离措施，不能声称已经消失。第三方已取得的副本无法由本站保证删除。
4. 保留摘要存在猜测验证与关联风险：随机 UUID 或时间不等于隐私保证；裸 `content_sha256` 尤其能验证猜测文件。不得把证明副本称为无隐私风险，承诺字段、文件名与保留期限在实施前审查。

本地只读实验工具 [`verify_redacted_chain.py`](../../tools/verify_redacted_chain.py) 检查合成实验格式的链折叠及可选独立检查点，显式将引用、删除授权和比特币验证标为未核验。它不是公开镜像核验器、不读取线上格式、不执行删除；不得将实验成功当作 P2 已实现。

### 阶段 P3：证明副本

拟定时把链条目、锚点和 `.ots` 推送到不受本站控制的位置。这一层不包含原文，但摘要仍可能泄露可猜测内容的存在或产生关联，必须先评估隐私和目的地。

作用：运营者如果改写历史，外部已经留有旧链头。这是成本最低的防篡改加固，也弥补了 RFC 0030 提到的“截断只有和其他镜像比较才能发现”。

建议目的地：公开 GitHub 仓库，加一个 Internet Archive item。

### 阶段 P4：内容副本

1. `mirror-pull` 增加附件下载：清单列出公开附件，按 `content_sha256` 校验，可断点续传、增量同步，并有大小上限。
2. 默认关闭；作者针对具体快照、附件和目的地选择授权，详细范围与撤销规则见[归档授权契约](0032-archive-authorization-contract.md)。
3. 内容推送到第二家云和 Internet Archive，只包含已授权的作品。
4. 删除声明具备认证和防回滚机制并通过验收后，才可据此同步移除我方控制的副本；不得依据未认证清单自动删除。

**为什么要作者授权。** 空白许可在本站的含义是“不自动授权他人复用”。现有两篇都不是开放许可：K4 写明再分发需事先书面许可；arXiv 那篇是授予 arXiv 的非独占分发许可。本站没有另设授予平台再分发权的使用条款。平台不能因为技术上能复制，就把全文推给第三方。

平台自己控制的私有异地副本属于备份，不是再分发，可以先做，也能先解决缺口 3 的主要风险。

### 暂缓

**Zenodo 自动投递：** 作者想要 DOI 时可以自行投递。平台代投需要逐项确认，因为其政策和作品范围由 Zenodo 决定，不属于本站发表规则。

**Arweave：** 只有同时满足以下条件才重新评估：

- 有作者明确要求永久保存。
- 作者逐个快照确认，确认页写明写入后无法撤回。
- 有冷静期，让作者有时间发现误传的隐私内容。
- 已开放许可或作者明确授权。
- 平台代付，有总量上限，不让作者持有钱包。
- 用户单独批准真实资金和公共链交易。

### 被放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 全文写入比特币 | 区块上限约 4 MB 权重，容量和费用都不现实 |
| 全站默认写入 Arweave | 官方文档说明上传后[实际上无法从网络移除](https://docs.ar.io/build/run-a-gateway/manage/content-moderation)，网关只能各自屏蔽。这与 CHARTER 的隐私和违规处理冲突 |
| 只用 IPFS | [IPFS 文档](https://docs.ipfs.tech/concepts/persistence/)说明节点会回收缓存，要长期保留必须 pin，仍然需要有人持续运行 |
| Filecoin | 存储按约定期限提供，到期后谁续约是治理问题，且增加代币支付环节。本 RFC 未查到其官方文档中的期限说明，不写具体数字 |
| 自建链或代币 | ADR 0003 明确不做 |
| 全站内容默认推给第三方 | 与作者许可冲突 |

**真实案例：** 2026-10-31，站长邮箱曾出现在链上账户记录的公开显示名中，因为尚未被锚定，才得以清除。如果当时写进的是不可删除的存储，这个邮箱会永久公开。

## 对平等参与的影响

不增加任何门槛。发表不依赖归档授权、钱包、付款或 AI 结果。不同意第三方归档的作者，发表、时间证据和讨论都不受影响，P1 完成后拟对所有公开附件生效。页面不把“已归档”显示成质量或可信度标记。

## 信任与权限

- P1 后，运营者仍能写入假文件，但无法在已有锚点之后不被发现地替换它。
- 附件进链只证明“这些字节不晚于某时刻存在”，**不证明作者身份、原创性或正确性**。作者归属要靠 O4 作者签名。
- 记录链摘要和归档推送由定时任务完成，不进入网站进程。推送失败不影响发表，但要告警。
- 上传内容按不可信数据处理。归档任务只搬运字节，不解析或执行。
- 外部凭证放在 `/etc/eksmu`，只有归档任务可读，不写进仓库或镜像。

## 数据与迁移

- 新增：`material` 记录类型、`redactions` 列表、归档授权字段、`eksmu.public-mirror.v2`。
- 旧版本记录的摘要不变；旧锚点继续有效。
- 补链会使链变长，属于正常追加。
- 迁移前先做备份，并在线上数据副本上演练。
- 现有镜像的使用者需要升级核验工具，SPEC 写明版本差异。

## 验收与反例

- **正常：** 作者上传 PDF，下一次锚定后，作品页显示该 PDF 摘要被某区块覆盖。第三方只用公开文件和核验工具就能走通，再用自己的比特币节点运行 `ots verify`。
- **新人：** 第一次发表的作者不做任何额外选择，就能得到附件时间证据；不开启归档也没有任何降级。
- **替换文件：** 改动已锚定附件的一个字节，核验失败。
- **隐私事故：** 作者误传含身份证号的文件。移除后内容从站点和我方副本消失，链仍校验通过，报告列出这次移除，已确认的锚点不受影响。
- **许可：** 未授权作品的字节不出现在任何第三方推送中，用测试明确验证。
- **滥用：** 批量上传垃圾附件，受现有配额（单文件 32 MiB、每作者 256 MiB、每版本 16 个）限制，不产生外部费用。
- **运营者截断：** 把链截短重建后，与证明副本中的旧链头比较能发现。
- **失败条件：** 任何页面把附件进链写成论文被验证、被证明正确或作者身份已确认，都算不通过。

## 外部事实来源（2026-11-06 查询）

- Internet Archive：[ias3 接口](https://archive.org/developers/ias3.html)、[版权政策说明](https://help.archive.org/help/rights/)。接到侵权通知后会移除内容。
- Arweave：[协议文档](https://docs.arweave.org/developers/development/protocol)、[AR.IO 网关内容管理](https://docs.ar.io/build/run-a-gateway/manage/content-moderation)。
- IPFS：[Persistence, permanence, and pinning](https://docs.ipfs.tech/concepts/persistence/)。

## 2026-11-07 确认的两层分布式保存架构与三步实施计划

2026-11-07，针对“用分布式数据链保存每个人的文章是否可行”的评估，确认采用**“两层分布式架构”**：
- **第 1 层（不可篡改的密码学索引与时间账本）**：`eksmu.record-chain.v1`（SHA-256 顺序摘要链）+ OpenTimestamps 比特币区块锚定 + `eksmu.public-mirror.v2` 公开镜像。只存结构化记录与所有附件字节的 SHA-256 承诺（`material` 记录），轻量、零链上手续费门槛，任何一台普通电脑几秒钟即可离线重算。
- **第 2 层（按内容寻址的分布式文件层）**：文章与附件（PDF、LaTeX 源码包、编译产物、数据）以 `sha256` 命名保存在内容寻址对象存储（`blobstore`）、可迁移完整备份包及授权镜像中。任何副本只要字节的 `SHA-256` 与第 1 层记录链中的 `material.payload.content_sha256` 一致，就自动继承比特币区块时间戳的数学证明，无需信任提供文件的节点，同时保留误传隐私或侵权附件时的移除能力（移除字节后摘要链不断裂）。

### 三步工程落地计划

1. **第一步（P1 生产化：附件哈希入链与作品页逐文件时间证据）**
   - 在 `eksmu/material_chain.py` 与 CLI `python -m eksmu --db <db> reconcile-materials` 中提供生产级幂等附件入链：逐个核验 `research_files` 的实际存储字节与 `sha256`/`size`，写入确定性 UUIDv5 的 `material` 记录并进入 `record_chain`（标明 `backfilled: true`）。
   - 在作品页 `/w/<id>` 的“本版材料”列表中，为每个已入链附件展示链位置 `#seq`、补链标识、比特币锚定区块号（或待锚定状态）以及单条材料记录链证明链接 `/api/chain/proof?record=<material_record_id>`；在“时间证据”面板中如实展示本版附件的入链与锚定覆盖情况（未入链时保持“不覆盖 PDF、源码等附件”的明确提示）。
2. **第二步（单文件／单篇作品离线独立核验）**
   - 在独立核验工具 `tools/eksmu_verify.py`（及公开协议仓库 `eksmu-protocol`）中新增 `verify-file <mirror_or_proof> <file>` 命令：作者或读者下载任意 PDF／LaTeX 源码包后，只需一条命令即可离线计算本地文件 `SHA-256` 与字节数，在镜像 `manifest.json` 或单条证明 JSON 中定位对应的 `material` 记录、核验其在 `record_chain` 中的折叠路径及覆盖它的比特币锚点。
3. **第三步（含完整附件字节的可迁移备份与异地恢复）**
   - 在 `eksmu/backup.py` 与 `python -m eksmu --db <db> backup <dest> --portable-blobs`（以及每日运维备份脚本）中支持将外部 `blobstore` 中的所有内容寻址附件字节一并打包并写入 `backup-manifest.json` 校验清单，`verify-backup` 逐字节校验所有 blob，`restore` 自动恢复完整 `blobstore`，确保异地独立机器单靠备份归档即可完整恢复正文与全部附件。
