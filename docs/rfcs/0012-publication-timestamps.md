# RFC 0012：发表版本的时间证据与先后比较

日期：2026-09-22。状态：方案草案；M4私有本地承诺已实现，公共时间戳服务未接入。

> 2026-10-08 更新：用户批准记录链与 OpenTimestamps 锚定，已按 [RFC 0029](0029-record-chain-and-anchoring.md) 实现：每日锚定的是全站记录链头，不是单个快照承诺；快照级 `DisabledAnchor` 与 `oic.local-time-evidence.v1` 的 `external_proof=null` 保持不变。用户明确提出用区块链时间戳为学术发现与发表的先后判断提供可信依据；本RFC的协议候选、数据字段、界面及验收由AI整理，尚未逐项定案。

M3已交付[固定正文/资料/附件快照和离线内容核验](0015-publication-snapshots.md)，为本RFC提供内容基础。

2026-09-23更新：私有本地承诺、证据包和离线核验已按[RFC0016](0016-local-time-evidence.md)实现。仍无外部锚定、链上证明、公开发表事件或作者身份核验；本RFC后续外部方案保持草案状态。

同日后续：快照页分开呈现时间来源，外部锚定的禁用态与候选工具预检边界见[RFC0017](0017-external-anchor-preparation.md)。没有进行真实提交或证明升级。

## 目的与证据范围

让研究者保存一个具体版本的可携带时间证明，第三方可以不依赖本平台数据库独立核验，并将它用于发现与发表先后的讨论。论文、证明、数据、代码、反例和阶段性探索都可以记录；没有时间证明仍可发表、讨论和获得评价。

在所用哈希算法和区块链验证假设成立时，完整证明支持“这些特定字节在相应区块形成前已经存在”。它不能单独证明谁最早想到、谁原创、内容正确，或当时已向公众开放。区块头时间也不能当作精确到秒的发现时刻。

例：甲周一存证，乙周二存证，只说明甲目前出示的链上存证更早，不能排除乙周日已有未存证草稿。甲先秘密存证、乙先公开发表，应展示两个事件及各自证据，不能自动把秘密存证等同于首次公开发表。内容的具体程度、独立发现、合作贡献及外部既有文献仍可讨论；模糊题目不能自动占有后来所有相关发现。

## 与当前实现衔接

当前`oic/store.py`保存作品与版本、平台UTC记录和内容摘要；这些是本地记录，管理员掌握数据库与时钟，不具有外部时间证明。`oic_receipts`的签名对象是有限计算回执，不能改称作者签名或链上时间证据。

`oic/research.py`的附件可以在正文版本发表后追加，RFC0011已说明这一点。因此要建立**不可变的存证快照**：锁定当时的正文版本和逐项附件清单，后添附件生成新快照与新证明，不继承正文最初的时间证据。现有作品、讨论与协作入口继续使用，不另建平台。

## 建议流程

1. 作者选择具体版本及需要包含的材料，本地生成快照。完整论文与阶段性探索使用同一机制。
2. 快照固定正文原始字节、版本引用、作者/贡献声明以及每份附件的摘要和长度。作者若选择签名，签名及其公钥标识在存证前纳入承诺；签名仅说明某密钥签署，不自动证明真实身份或原创。
3. 对快照加入独立随机数形成承诺。候选采用OpenTimestamps的标准证明与聚合机制，多个承诺可以汇总到一个Merkle根，不要求每篇论文单独发送交易。不要自创一条由本平台独自控制的链并称其消除了平台信任。
4. 取得待完成回执后继续更新证明；只有完整路径及对应链状态实际核验通过，才展示相应已核验状态。发表不等待区块确认。
5. 导出原始材料、快照、必要随机数、可选作者签名及完整证明。独立核验器重算内容绑定与链上路径；材料和证明分别备份，链上摘要不负责保存论文。

当前只设计上述流程，不调用`ots stamp`、公共calendar或广播接口。即使由第三方代为广播、没有直接操作钱包，也属于外部存证，不能绕过项目当前私有约束。

## 候选数据契约

以下是字段语义草案，不是已发布的API或可直接导入的格式。实现前固定格式版本、字节编码、规范化规则及测试向量；核验以保存的原始快照字节为准，不能依赖PDF重新导出、Pandoc渲染或重新排版后仍相同。

| 对象 | 必须表达的内容与边界 |
|---|---|
| 存证快照 | 格式版本、作品/正文版本标识与摘要、所选材料的稳定标识/摘要/字节长度、贡献声明、上一快照引用；遗漏的附件不得被标为已存证 |
| 身份关联 | 化名/账号声明、可选作者公钥和预先签署的声明、平台接收回执分别保存；现有账号令牌及其认证摘要不当作公开签名密钥 |
| 内容承诺 | 快照摘要、算法、随机数及明确的承诺构造；随机数保存在作者证据包中，不写入公开批次清单。摘要不是加密，私有随机数丢失可能使证明无法重新关联原文 |
| 时间事件 | 作者自述发现时间、平台接收时间、公开发表事件及其可访问/见证证据、存证请求时间分别记录；任何自述或平台时钟字段即使被存证，也不会自动成为事实 |
| 链上证明 | 证明格式与原始字节、网络、区块高度及哈希、区块头所载时间、验证时观察到的链尖/确认数；本地和测试网络必须标明 |
| 核验记录 | 核验器及版本、核验时间、内容绑定结果、节点或第三方数据来源、确认策略、失败/未完成原因；缺少材料时仅能检查承诺路径，不能声称已核验论文内容 |

公开发表记录可以由平台签署并接受独立见证，但链上时间戳只支持这些记录的存在时间，不能单独证明过去某URL可公开访问。补录的旧稿和外部证据保留来源与核验范围。

## 状态与先后比较

建议区分：`local_only`（仅本地快照）、`pending`（已有未完成外部回执）、`anchored_unverified`（取得完整证明但尚未独立核验）、`verified`（在记录的链状态与策略下通过）、`invalid`（明确不匹配）、`unavailable`（材料或节点不可用）、`recheck_required`（链状态变化等需重检）。状态与核验历史分开保存；一次网络失败不等于内容造假。

界面展示“平台记录”“首次公开发表记录”“区块链时间证据”，而非一个没有来源的“发现时间”。核验结果给出范围与来源，避免只显示认证勾选图标。

- 在同一条已核验链上，可以比较锚定区块的先后；这比较的是存证记录，不是创作或发现的实际先后。
- 同一批次或同一区块不能用Merkle叶子位置、交易位置或平台数据库序号裁决发现先后。平台接收顺序最多作为单独标注的辅助记录。
- 不同链的区块高度不可直接比较，区块时间也不是精确统一时钟。时间范围重叠或证据不足时保留无法判定，不能强制选出胜者。
- 后来出现更早的可验证证据，允许追加并重新讨论。已有论文不因新证据被静默改写或失去发表资格；争议记录指向具体主张、版本与贡献。

区块重组、确认不足和验证器失联分别呈现，不能将暂时收录写成永久不可撤销。确认策略在实际接入前明确，不在本草案中武断指定统一阈值。任何优先权讨论都允许补充平台外证据，不以是否购买更快服务排序学术权利。

## 隐私、可迁移性与费用

正文、私人数据、作者账号凭据不上公共链。随机化承诺减少从摘要猜测内容的风险，但不消除提交时间、IP或关联信息；批量聚合也不是完全匿名。当前私有阶段连承诺都不发送给公共服务。

发表和基本参与不要求钱包、购币或支付gas。候选由平台或可替换的服务处理聚合与运行成本；具体预算、服务选择和公开启用另行确定。时间证明不依赖项目发币或资金合约。

完整证明应能在本平台停运后验证。未完成回执仍依赖calendar补齐路径，必须保存升级后的证明；独立验证需要合适的链数据。若使用第三方查询服务，应说明新增信任与数据去向。外部证明中的URL不能自动触发任意网络访问，导入与核验应限制大小、深度及允许的网络目标。

## 实施顺序与验收建议

先与A1发表版本、P3备份恢复同步定义快照与导出契约，再做私有离线原型；公共锚定接入是后续独立步骤。本轮没有改变P3可靠多人试用的主工程。

离线阶段的验收应覆盖：正文或附件变更后旧证明不再适配；后添材料不继承旧存证；作者关联不能被更换；规范化与原始字节能独立复算；丢失随机数或材料时诚实报告局限；没有网络也能发表；待完成/模拟证明不能标为已上链；导出后在独立环境重建内容绑定。只演练这些检查不能称为已验证真实区块链。

正式接入前另行验证：真实证明升级与独立链核验、确认/重组处理、服务失联与恢复、同批次并列、不同链不可直接排序、完整证据包备份恢复，以及不经平台的独立复核。以下来源核对不替代这些实现与测试。
